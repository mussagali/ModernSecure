## 0. Инструкция AI-агенту: прочитать до начала разработки

Ты — senior full-stack/mobile engineer, product architect и security-minded разработчик. Реализуй проект по настоящей спецификации, **а не демо-макеты**. Работай последовательно: анализ репозитория → план → схема данных и RLS → авторизация → вертикальный рабочий сценарий → остальные экраны → тесты → подготовка к выпуску.

### Неизменяемые правила

1. **Flutter (Dart)** — нативно ощущающееся приложение **только для клиентов** на **Android и iOS**. Не создавать роли юриста, менеджера и администратора в Flutter.
2. **React + TypeScript + Vite** — **только веб-панель сотрудников** для **юриста, менеджера, администратора**. Клиент **не пользуется этим сайтом**.
3. **Supabase** — единый слой данных и сервисов: Auth, PostgreSQL, RLS, Storage, Realtime; Edge Functions и PostgreSQL RPC/triggers для доверенных операций. **Не поднимать самостоятельный Node/Nest/Express/Django/FastAPI backend**.
4. В приложении и вебе использовать **один Supabase project / один источник данных** для конкретной среды. Test и production должны быть изолированы.
5. Роли проверяются **на уровне БД/RLS и безопасных серверных функций**, а не только в навигации. UI-guard — лишь дополнительная защита.
6. **Никаких service_role/secret keys в Flutter, браузерном JavaScript, публичном репозитории или мобильной сборке.** Использовать публичный publishable key и пользовательскую сессию.
7. Только **приватные** юридические документы. Ни публичных Storage buckets, ни бессрочных открытых URL.
8. Не показывать клиенту внутренние заметки сотрудников; не передавать их в клиентские запросы и подписки Realtime.
9. При отсутствии интеграции или настоящей проверки безопасности **не имитировать успех**. Мок-данные разрешены только в явно помеченной dev/demo среде.
10. Следовать требованиям локализации персональных данных в РК до production: основная БД, файлы и бэкапы с персональными данными — на инфраструктуре в Казахстане; маршрут внешних данных дополнительно согласовать с заказчиком/юристом.
11. Если существующий код противоречит этой спецификации, предложить минимальный безопасный план миграции. Не удалять файлы и данные без необходимости.
12. Поддерживать русский язык для MVP, но все тексты готовить к будущему переводу на казахский (i18n).

### Что НЕ разрабатывать

- Клиентский веб-кабинет.
- Мобильное приложение для сотрудников.
- WebView как основную технологию мобильного интерфейса: Flutter должен рендерить собственные экраны.
- Отдельный API-сервер, ORM-сервер, микросервисы бизнес-логики или вторую БД.
- Публичную самостоятельную регистрацию клиента.
- CRM-интеграцию, онлайн-эквайринг, ЭЦП, госинтеграции, OCR, WhatsApp/SMS-рассылки, push-уведомления в MVP без отдельного подтверждения.
- AI-оценку вероятности успешного банкротства или выдуманный процент «готовности дела».

## 1. Суть продукта

**«Современная защита»** — цифровое сопровождение юридических дел, начиная с услуги банкротства физических лиц в Казахстане.

**Клиент в Flutter:** понимает, где находится его дело, что уже сделано юристом, какие документы нужны, что он должен сделать сейчас; общается с юридической компанией и видит договор и подтвержденные платежи.

**Сотрудники в React Web:** работают с реальными делами через одну веб-панель с разными правами. Юрист ведет юридическую часть и документы, менеджер общается с клиентами и работает с договорами, администратор настраивает сотрудников, доступы, услуги и шаблоны.

### Итоговое распределение платформ

| Роль | Flutter Android/iOS | React Web | Назначение |
|---|:---:|:---:|---|
| **Клиент** | **ДА** | **НЕТ** | Свои дела, документы, задачи, чат, оплаты |
| **Юрист** | НЕТ | **ДА** | Юридическая работа по назначенным делам |
| **Менеджер** | НЕТ | **ДА** | Клиенты, договоры, коммуникация, организация работы |
| **Администратор** | НЕТ | **ДА** | Пользователи, назначения, услуги, шаблоны, настройки, аудит |

В одной компании может быть много юристов/менеджеров; у клиента может быть несколько дел. Каждое дело имеет собственный набор документов, задач, сообщений, этапов, оплат и участников.

## 2. Выбранный технологический стек

### 2.1. Клиент: Flutter

- **Flutter** (актуальная стабильная версия) + **Dart**.
- `supabase_flutter` — Auth, SQL-подобные запросы к Data API, Storage, Realtime, вызовы Edge Functions.
- **Riverpod** — state management и dependency injection.
- **go_router** — роутинг и защищенные маршруты.
- `freezed`/`json_serializable` либо эквивалент — типизированные модели.
- `image_picker`, `file_picker` — камера, галерея и документы, с платформенной обработкой разрешений.
- `flutter_secure_storage` — при необходимости секреты, для которых безопасное хранилище предусмотрено проектом; не дублировать сессию бессистемно.
- `intl` и Flutter l10n — даты, суммы и будущая локализация.
- Просмотр PDF/изображений — библиотека с поддержкой iOS/Android и авторизованных временных URL; открытие и скачивание без открытых ссылок.
- Design: адаптивный Material 3 с аккуратными iOS-паттернами, ощущение качественного native-приложения; не копировать внешне iOS в ущерб Android.

### 2.2. Сотрудники: React Web

**Выбор: React + Vite, не Next.js.** Причина: приватная авторизованная SPA-панель без SEO и публичного SSR; проще деплой, меньше ненужной серверной логики, прямое подключение к Supabase через безопасные RLS-политики.

- **React + TypeScript + Vite**.
- **React Router** — защищенные маршруты и nested layouts.
- **TanStack Query** — загрузка/мутации, cache invalidation, retries.
- **Tailwind CSS + shadcn/ui + Radix UI** — качественные формы, диалоги, таблицы.
- **React Hook Form + Zod** — валидация форм; авторитетная валидация повторяется в БД/Edge Functions.
- **Supabase JS v2** — Auth, PostgREST, Realtime, Storage, Edge Functions.
- **TanStack Table** — таблицы и фильтры дел/клиентов/платежей.
- **Lucide** — единый набор иконок.
- Локализация через `i18next` или аналог.
- Производительная SPA, responsive от 360 px, с desktop-first рабочими таблицами.

### 2.3. Backend-as-a-Service: Supabase

- **Supabase Auth** — email/password, сессии, восстановление доступа, MFA для сотрудников.
- **PostgreSQL** — реляционная модель и транзакции.
- **RLS + GRANT/REVOKE** — разграничение на уровне каждой строки и операции.
- **Supabase Storage** — только приватные buckets, отдельные политики доступа.
- **Supabase Realtime** — новые сообщения, изменившиеся дела, уведомления; ограничения подписок по правам.
- **Edge Functions** — доверенные операции: выдача приглашений, изменение ролей, администрирование Auth-пользователей, безопасные файлы и другие сценарии, где нельзя доверять клиенту.
- **Postgres functions (RPC), constraints, triggers** — атомарные операции по этапам, оплатам, аудиту, дедупликации.
- **Supabase CLI / SQL migrations / seed** — схема как код, миграции и безопасные демонстрационные данные.

**Важно:** Edge Functions и SQL RPC — часть архитектуры Supabase, **не отдельный кастомный backend-сервер**. Их разрешено использовать, но не создавать сервер ради обычного CRUD.

### 2.4. Production в Казахстане

Исходное ТЗ требует локализации персональных данных. Для production следует запланировать **self-hosted Supabase в дата-центре РК** (либо эквивалентную согласованную инфраструктуру, соответствующую требованиям). Выбор региона и схема трансграничных передач требуют юридической проверки до запуска.

Self-hosting означает, что команда отвечает за Docker-сервисы, TLS, бэкапы, восстановления, обновления, мониторинг и защиту. **Не предполагать**, что managed backups, PITR и другие услуги Supabase Cloud автоматически доступны при self-hosted. Для локальной разработки можно использовать Supabase CLI; это **не** production-хостинг.

Документация: https://supabase.com/docs/guides/self-hosting

## 3. Изменения относительно исходного ТЗ

| В исходном ТЗ от 07.10.2026 | Итоговое решение для разработки |
|---|---|
| Адаптивный веб-кабинет клиента + WebView приложения | **Нативный Flutter-клиент**, без клиентского веб-интерфейса |
| Отдельная веб-панель сотрудников | **React Web** для юриста, менеджера и администратора |
| Телефон + SMS одноразовый код как базовый вход | **Email + пароль** для клиента и сотрудников (актуальное ранее выбранное заказчиком решение) |
| Backend / API / сервер кабинета | **Только Supabase**, без собственного backend-сервера |
| SMS для входа входит в исходный базовый объем | **Не нужен** при входе по email/password; SMS-авторизацию считать изменением scope |
| Push уведомления отдельно | В MVP **центр уведомлений внутри приложения и веба**, push позже |
| Проверка файлов на вредоносность обязательна | Сохраняем требование; **production blocker**, пока нет реального механизма сканирования |

Важное правило: это **осознанные изменения требований**, не случайное упрощение. Если заказчик позднее решит вернуть SMS, клиентский сайт или WebView, оформить отдельное изменение scope.

## 4. Полный состав функций Flutter-приложения — только клиент

### 4.1. Экран запуска / доступ

**Экраны:** splash → вход по email/password → восстановление пароля → первое принятие условий → главный экран.

- Клиент **не регистрируется самостоятельно**: сотрудник создает ему доступ или отправляет приглашение.
- Вход через Supabase Auth email/password.
- Сообщения об ошибке, неверном пароле, заблокированном доступе, отсутствии сети.
- Восстановление пароля через проверенное письмо/deep link.
- Подтверждение версии согласия на обработку персональных данных; отдельное необязательное согласие на маркетинг.
- Автоматическое восстановление валидной сессии, корректный logout.
- Если роль текущего пользователя не `client`, Flutter не предоставляет вход в функциональность и безопасно завершает маршрут.
- Изменение email и идентификационных полей — через контролируемый компанией процесс проверки.

### 4.2. Нижняя навигация: ровно 4 вкладки

1. **Главная**.
2. **Моё дело**.
3. **Документы**.
4. **Сообщения**.

Профиль, договор, оплаты, уведомления, FAQ и контакты — через кнопку профиля/настроек на верхней панели и контекстные ссылки; **не добавлять пятую-шестую вкладку**.

### 4.3. Главная

**Цель:** показать главное за 5–10 секунд, без перегрузки интерфейса.

- Имя клиента, название услуги, выбранное дело; переключатель, если дел несколько.
- Текущий юридический этап, дата последнего официального обновления и ответственный юрист.
- **Главный акцент: блок «Что нужно сделать»** с активной задачей, дедлайном, CTA.
- Если задач нет: «Сейчас от вас ничего не требуется».
- Блок последних официальных событий дела и следующего шага.
- Документы на исправлении (с комментариями и переходом к повторной загрузке).
- Ближайший платеж и статус подтвержденных оплат.
- Количество непрочитанных сообщений/уведомлений.
- Состояния загрузки, отсутствия данных, ошибки, нет подключения.

### 4.4. Моё дело

- Карточка конкретного дела: название услуги, номер/дата (если есть), юрист, текущее состояние.
- **Таймлайн этапов**, включая историю реально опубликованных действий (не фиктивные проценты).
- Плановый срок обозначать как **ориентировочный**.
- История изменений: дата, что сделано, что будет дальше, при наличии файлы/подтверждения.
- Просмотр выполненных, текущих и ожидаемых этапов; тексты этапов формируются из шаблона услуги.
- Признаки «Требуется ваше действие», «Приостановлено» — отдельно от этапа, с пояснениями.
- Если дело завершено — фактический результат, итоговые документы, дальнейшие действия.
- Внутренние заметки, правки других дел и скрытые служебные поля не показывать и не запрашивать.

### 4.5. Документы

- Список запросов документов по **выбранному** делу.
- Статусы: `Нужно загрузить`, `Проверка безопасности`, `На проверке у юриста`, `Принят`, `Нужно исправить`, `Не требуется`.
- В карточке запроса: название, обязательность, инструкция, срок, пример, комментарий юриста, список отправленных версий.
- Выбор через камеру/галерею/файлы; поддержка **PDF, JPG, JPEG, PNG, HEIC**.
- Дефолтные лимиты исходного ТЗ: **20 МБ на файл, 10 файлов и 100 МБ на отправку**; изменяемые настройки.
- До отправки — превью списка, удаление выбранного, порядок страниц; показывать прогресс каждого файла и общий статус.
- Успешное завершение показывать **только после подтвержденного сохранения**.
- Сетевой сбой — безопасная повторная попытка без дубликатов; сохраненные файлы не теряются.
- При возврате юристом — комментарий обязателен; клиент отправляет **новую версию**, старая сохраняется.
- Принятые документы клиент не перезаписывает и не удаляет.
- Просмотр/скачивание доступных файлов только по авторизованному короткоживущему доступу.
- До завершения фактической антивирусной проверки **карантинный файл нельзя открыть ни клиенту, ни сотруднику**.
- Показатель комплектности = принятые обязательные запросы / обязательные активные запросы, **не** «процент завершения юридического дела».

### 4.6. Сообщения

- Один общий диалог клиента с командой **на каждое дело**.
- Текст и разрешенные вложения, имя автора, время и статус прочтения.
- Реальное обновление через Supabase Realtime, пагинация истории.
- Отправка с idempotency key: повтор при сбое не создает дубль.
- Индикатор непрочитанного, переход по уведомлению в нужное дело.
- В MVP **нельзя редактировать или удалять отправленные сообщения**.
- Показывать рабочие часы, ориентировочное время ответа, контакты / системную ссылку на WhatsApp.
- Внешние WhatsApp-сообщения не выдавать за сообщения, сохраненные внутри системы.

### 4.7. Задачи клиента

- Доступны с Главной и Моего дела.
- Типы: загрузить документ, ответить на вопрос, подтвердить ознакомление, связаться с компанией.
- Статусы: новая, ответ отправлен, выполнена, отменена; отдельно просрочена по дате.
- Название, инструкция, назначенный срок, связанные документы.
- Клиент отправляет ответ/материал; для проверяемой задачи юрист подтверждает выполнение или возвращает на доработку.
- Подтверждение ознакомления сохраняет пользователя, версию текста и время. **Это не ЭЦП и не юридически значимая электронная подпись.**

### 4.8. Договор и оплаты

- Договор в PDF, приложения, номер и дата, стоимость юридической услуги.
- Список подтвержденных платежей, задолженность, график платежей и ближайшая дата.
- Клиент может отправить фото/файл чека; статус **«На проверке»**.
- Чек **не считается оплатой**, пока сотрудник с разрешением не подтвердит платеж.
- Поддержать частичные оплаты; сумма и остаток рассчитываются по подтвержденным записям.
- Реквизиты компании из настроек.
- **Онлайн-оплата/эквайринг не входит в MVP.**

### 4.9. Уведомления, профиль и помощь

- In-app центр уведомлений: возврат документа, новая задача, измененный этап, новое сообщение, приближающийся платеж.
- Счетчик непрочитанных, переход сразу к событию и отметка прочтения.
- Напоминания: за день до срока и в день срока, один раз на событие; отмененные/выполненные задачи не напоминаются.
- Профиль: ФИО, контактный email, телефон, город; ИИН только если необходим для услуги и в безопасном контексте.
- FAQ, часы работы, телефоны, WhatsApp, правила обработки персональных данных.
- Выход из аккаунта, состояние соединения, версии согласий.

## 5. Функции React Web — единая панель сотрудников

### 5.1. Общие возможности для всех сотрудников

- Вход по email/password, MFA для сотрудников, защита от подбора.
- **Отсутствие самостоятельной публичной регистрации.** Аккаунт сотрудника создает уполномоченный администратор.
- Ролевой маршрут: юрист, менеджер и администратор видят только разрешенные разделы.
- Dashboard с релевантными метриками, списки с поиском, фильтрами, сортировкой, пагинацией.
- Состояния ошибок, пустых списков, подтверждение опасных операций.
- История изменений с автором и временем; интерфейс не может редактировать аудит.
- Никакой «универсальной роли со всеми доступами» по факту одного лишь логина.

### 5.2. Юрист — Web

**Основной сценарий:** увидеть работу по своим делам → проверить документ → вернуть или принять → обновить этап → создать задачу → написать клиенту.

**Экраны и функции:**

1. **Рабочий стол `/lawyer/dashboard`**: активные назначенные дела, документы на проверке, просроченные задачи, непрочитанные чаты, давно не обновленные дела.
2. **Мои дела `/lawyer/cases`**: список только назначенных дел, поиск/фильтры/сортировка.
3. **Карточка дела `/cases/:id`**: клиент, услуга, этап, история, документы, задачи, договор в объеме права, чат, внутренние заметки.
4. **Документы `/lawyer/documents`**: очередь проверки, защищенный просмотр, принять / вернуть с обязательным комментарием / запросить дополнительное / отменить запрос с причиной.
5. **Этапы дела**: только разрешенные переходы по версии шаблона; публикация клиентского пояснения, следующего шага и ориентировочного срока; возврат на этап с обязательной причиной.
6. **Задачи**: создание/изменение/проверка задач клиента, срок, подтверждение выполнения, возврат на доработку.
7. **Сообщения `/lawyer/messages`**: чат по делу, вложения, непрочитанное, очередь приоритетов.
8. **Внутренние заметки**: отдельная вкладка, которая никогда не попадает в клиентское приложение.
9. **Завершение дела**: указать фактический результат (`удовлетворено` / `отказано` / `прекращено` / иной) и описание; без результата нельзя закрыть дело.

**Ограничения:** юрист не управляет всеми пользователями, ролями, системными настройками; не видит неназначенные дела. Подтверждение оплат — только при отдельном разрешении.

### 5.3. Менеджер — Web

**Основной сценарий:** организовать работу с назначенными клиентами, контролировать документы/коммуникации и договоры, направлять запросы юридической команде без самовольных юридических решений.

**Экраны и функции:**

1. **Dashboard `/manager/dashboard`**: назначенные клиенты, активные договоры, непрочитанные обращения, ближайшие платежи, ожидающие организационные действия.
2. **Клиенты `/manager/clients`**: список **назначенных** клиентов, поиск по ФИО, телефону и номеру договора; ИИН маскировать.
3. **Профиль клиента `/clients/:id`**: контакты, его дела, статус сотрудничества, договоры, коммуникации — в рамках доступа.
4. **Договоры `/manager/contracts`**: создание/загрузка договора, приложений и данных графика при наличии соответствующих прав.
5. **Платежи `/manager/payments`**: просмотр графика, чеков, статусов; **подтверждение оплат только с отдельным permission**.
6. **Коммуникации `/manager/messages`**: чат в доступных делах, ответы по организационным вопросам.
7. **Поручения/напоминания**: контроль документов и организационных задач, уведомление ответственного юриста.

**Ограничения:** по умолчанию менеджер **не меняет** юридический этап, результат дела, юридическое решение по документам и роль пользователя. Для дополнительных функций нужны специальные разрешения (не просто изменение кнопок).

### 5.4. Администратор — Web

**Основной сценарий:** настроить организацию, сотрудников и процессы без автоматического доступа к каждой юридической папке.

**Экраны и функции:**

1. **Dashboard `/admin/dashboard`**: общее количество активных/завершенных дел, очереди, документы и задачи, системные оповещения (только агрегированные показатели и допустимые метаданные).
2. **Сотрудники `/admin/staff`**: приглашения, активация/блокировка аккаунтов, роли, назначенные права, MFA compliance, отзыв сессий.
3. **Клиенты `/admin/clients`**: создание доступа через приглашение, проверка контактов, связывание пользователя с делом, блокировка/архивация по утвержденной процедуре.
4. **Дела `/admin/cases`**: создание, назначение и переназначение юриста/менеджера, архивирование, управление маршрутом. **Просмотр содержимого** документов/чатов — только при отдельно выданном праве.
5. **Услуги `/admin/services`**: справочник видов услуг.
6. **Шаблоны этапов `/admin/stages`**: маршруты, допустимые переходы, версионирование. Изменение шаблона не переписывает историю уже созданных дел.
7. **Шаблоны документов `/admin/document-templates`**: списки, обязательность, описания, примеры.
8. **Роли и permissions `/admin/permissions`**: отдельные права на оплату, массовую выгрузку, удаление, доступ к делу, просмотр ИИН.
9. **Настройки `/admin/settings`**: бренд, реквизиты, часы работы, контакты, FAQ, инструкции, тексты уведомлений, лимиты файлов.
10. **Аудит `/admin/audit`**: фильтрация событий входа, назначения, доступа, скачивания, действий с документами, этапами и оплатами; журнал только для чтения.
11. **Диагностика системы**: ошибки операций, состояние бэкапов/проверок и очередей через безопасный администраторский экран или отдельный защищенный operational dashboard, без секретов.

Админ управляет организацией, но **не обязательно имеет доступ ко всем чувствительным файлам**. Требуются явные разрешения `case_content.read`, `documents.read`, `payments.confirm`, `exports.bulk`, `data.delete`, `pii.full_read`.

### 5.5. Условная матрица доступа MVP

Обозначения: **✓** — разрешено в рамках своего контекста, **P** — только отдельное permission, **—** — запрещено.

| Операция | Клиент (Flutter) | Юрист (Web) | Менеджер (Web) | Админ (Web) |
|---|:---:|:---:|:---:|:---:|
| Просмотр своего дела | ✓ | — | — | — |
| Просмотр назначенных дел | — | ✓ | ✓ (метаданные) | ✓ (метаданные) |
| Чтение содержимого чужого/неназначенного дела | — | — | — | P |
| Загрузка клиентских файлов | ✓ | ✓ | P | P |
| Проверка юридических документов | — | ✓ | P | P |
| Публикация юридического этапа | — | ✓ | P | P |
| Ответ в разрешенном чате | ✓ | ✓ | ✓ | P |
| Просмотр внутренних заметок | — | ✓ | P | P |
| Просмотр своих договоров/платежей | ✓ | P | ✓ | P |
| Создание договоров/графика | — | P | ✓ | P |
| Подтверждение денежных поступлений | — | P | P | P |
| Создание пользователей и назначений | — | — | — | ✓ |
| Управление ролями/шаблонами/настройками | — | — | — | ✓ |
| Массовая выгрузка / удаление данных | — | — | — | P |

**Примечание:** матрица задает целевое UX-поведение; итоговые RLS и permissions должны учитывать *принадлежность конкретному делу*, *назначение*, *тип операции*, *состояние*, *роль* и *дополнительное разрешение*. Административные агрегаты не должны раскрывать содержимое дел.

## 6. Архитектура данных Supabase

### 6.1. Принципы

- Все предметные таблицы — PostgreSQL с UUID первичными ключами, `created_at`, `updated_at`, `created_by`/`updated_by` где нужно.
- `auth.users` — источник идентичности; профиль и бизнес-роль связаны по `auth.uid()`.
- Пользователь может иметь **несколько дел**; дело в MVP принадлежит одному клиенту (сложные совместные дела — отдельный scope).
- Сотрудник получает доступ **через активное назначение на дело и/или явно выданное permission**.
- Не хранить права в изменяемых пользователем полях профиля. Роли и permissions — защищенная БД/проверенные app_metadata; изменения атомарны и аудируются.
- Служебные и внутренние поля держать отдельно от клиентских таблиц или представлений; не надеяться, что Flutter их не отрисует.
- Приватные данные возвращать только тем, кому это разрешено в БД, включая прямые ID-запросы, поиски, Storage и Realtime.

### 6.3. Статусы и правила в БД

**Статус документа:** `needs_upload` → `security_check` → `lawyer_review` → `accepted` / `needs_fix`; отдельно `not_required`.

**Статус задачи:** `new` → `response_sent` → `completed`; возможно `cancelled`. Просроченность вычисляется отдельно.

**Состояния дела:** `active`, `paused`, `completed`, `archived` (не путать с юридическим этапом). При `paused`: причина, инициатор и дата следующего контроля обязательны. При `completed`: фактический результат обязателен.

**Платежи:** `pending_verification`, `confirmed`, `rejected`, `adjusted` (корректировки — отдельные записи, не перезаписывать финансовую историю). Остаток = договорная сумма − сумма подтвержденных платежей с учетом корректировок.

**Атомарность:** переходы этапов, подтверждение платежа, изменение assignment и повторная загрузка документов должны выполняться транзакционно через защищенные RPC/Edge Functions. Ввести `version` или optimistic locking, чтобы два сотрудника не перезаписывали друг друга.

### 6.4. Минимальные инварианты

- Нельзя иметь активную ссылку на документ без существующего дела и запроса.
- Дело связано только с одним владельцем-клиентом; другой клиент не получает данные ни по UUID, ни по поиску, ни по Realtime.
- Чат, документы, платежи, задачи и уведомления всегда привязаны к **конкретному** делу.
- Старые версии документов и история смены этапов не затираются.
- Смена ответственного сотрудника прекращает предыдущий доступ, если нет другого активного назначения/разрешения.
- Изменение шаблона услуги не изменяет историю существующих дел.
- `client_message_id` уникален в рамках отправителя/дела для идемпотентной отправки.
- Подтверждение оплаты доступно только при явном праве и записывает автора.
- Серверное время — источник истины для истории; отображение дат по умолчанию `Asia/Almaty`, UTC+5 (Казахстан), пользовательские timezone — по согласованному сценарию.

## 7. Безопасность: обязательная часть реализации

### 7.1. RLS и SQL разрешения

Применить **RLS ко всем бизнес-таблицам, доступным через Data API**, с настройкой `GRANT`/`REVOKE` по минимально нужным операциям. Политики должны использовать авторизованную личность, роль и разрешенные связи с делом, а не `client_id` из тела запроса как источник доверия.

**Пример логики, не готовый SQL:**

```text
client_can_read_case(case_id) =
    signed_in_user.role == 'client'
    AND cases.client_id == auth.uid()

lawyer_can_edit_case(case_id) =
    signed_in_user.role == 'lawyer'
    AND exists active case_assignments(case_id, auth.uid(), 'lawyer')

manager_can_read_case(case_id) =
    signed_in_user.role == 'manager'
    AND exists active assignment(case_id, auth.uid(), 'manager')
    AND requested fields are allowed for manager

admin_can_read_case_content(case_id) =
    signed_in_user.role == 'admin'
    AND has_permission(auth.uid(), 'case_content.read')
    AND scope matches case_id
```

Структуры `security definer` применять осторожно: фиксировать `search_path`, ограничивать EXECUTE, проверять auth и ownership **внутри** функции, тестировать обходы.

**Запрещено:** `using (true)` для чувствительных таблиц; запись роли из обычного профиля; полный доступ админа к содержимому без отдельного permission; защита исключительно React/Flutter route guard.

Документация: https://supabase.com/docs/guides/database/postgres/row-level-security

### 7.2. Auth

- Вход email/password. Публичную signup-форму не показывать и не разрешать произвольное создание клиента, когда это можно исключить на уровне настроек Auth.
- Новых пользователей создает уполномоченный админ через **Edge Function** с проверкой прав и безопасным использованием admin auth API.
- Сотрудникам нужен MFA; при блокировке аккаунта — отзыв действующих сессий и немедленное прекращение авторизации через DB-проверку `is_active`.
- Восстановление/смена email после проверки; не пересылать пароли обычным письмом.
- Блокировать злоупотребление логином, приглашениями, выдачей токенов и секретами.

### 7.3. Storage и антивирусная проверка

- Storage buckets только приватные, разделение минимум `document-quarantine`, `case-documents`, `message-attachments`, `contracts`, `payment-receipts` (либо эквивалентная строгая модель).
- На клиенте разрешены только допустимые MIME/расширения/лимиты; **доверенная проверка** MIME, фактического типа и размера повторяется серверно.
- Загрузки в карантин по безопасным путям, без public URL и без возможности чтения до проверки.
- После реальной проверки файл можно перевести в доступное приватное хранилище или открыть защищенный read path; опасные файлы изолировать/отклонять.
- Превью PDF/изображений не должно исполнять произвольные скрипты/HTML.
- Важно: **Supabase Storage сам по себе не обеспечивает полноценное антивирусное сканирование, и SQL RLS его не заменяет.** Требование исходного ТЗ к антивирусной проверке нужно реализовать проверенным механизмом (например, согласованным сканирующим сервисом/процессом в KZ-инфраструктуре, запускаемым из доверенного pipeline). Это инфраструктурная зависимость; если пользователь категорически запрещает дополнительный security worker/provider, **обозначить функциональность как заблокированную для production, а не утверждать, что проверка есть**. Не создавать полноценный кастомный бизнес-backend ради сканирования.
- Signed URL только короткоживущие и выдаются авторизованному пользователю с доказанным доступом. Скачивания/просмотры писать в аудит.

### 7.4. Приватность и эксплуатация

- Передавать данные только по HTTPS, TLS errors не игнорировать.
- Редактируемые данные клиента, ИИН, платежи, юридические сведения — минимально необходимый объем.
- Убрать ПДн и секреты из console logs, crash reports, аналитики, пушей, URL, скриншотов тестов.
- Тестирование только на синтетических/обезличенных данных.
- Защитить от CSRF/XSS, injection, brute force, доступа по подмененным UUID, replay событий.
- Сбор/изменение/отзыв согласий, сроки хранения и удаление после юридического согласования.
- Бэкапы DB и файлов минимум раз в сутки, хранение ориентировочно 30 дней, проверенное восстановление; целевые исходные значения: **RPO 24 часа, RTO 8 часов**.
- Мониторинг ошибок, очереди сканирования, работы Realtime, объема диска, сертификатов и бэкапов.
- На тестовой среде явно запретить любые реальные персональные юридические данные.

## 8. Ключевые пользовательские сценарии (end-to-end)

### Сценарий A. Создание клиента и дела

1. Администратор в Web создает карточку клиента и приглашение на email.
2. Защищенная Edge Function создает/invites Auth-пользователя и профиль `client`; без клиентского `signUp`.
3. Админ создает дело, выбирает услугу и версию ее workflow, назначает юриста и при необходимости менеджера.
4. Клиент открывает Flutter, принимает приглашение/задает пароль, принимает обязательные условия.
5. Flutter получает через RLS **только его дело/дела**, название услуги и ответственного юриста.

### Сценарий B. Запрос документа → проверка → исправление

1. Юрист открывает назначенное дело и создает запрос документа из шаблона или индивидуальный.
2. Клиент видит его в Главной/Документах; загружает PDF/фото.
3. После успешного сохранения файл отмечается `security_check`, остается приватным в карантине.
4. Защищенный pipeline производит реальную проверку. Если безопасен — `lawyer_review`, иначе `rejected` с объяснением.
5. Юрист получает задачу на проверку; принимает или возвращает с обязательным комментарием.
6. Клиент видит `needs_fix`, читает замечание и загружает **новую версию**.
7. Предыдущий файл/решение остаются в истории. Все действия в аудите.

### Сценарий C. Смена этапа дела

1. Юрист выбирает допустимый переход для текущей версии workflow.
2. Указывает пояснение для клиента, следующий шаг, плановую дату, при откате — причину.
3. Защищенная транзакция проверяет active assignment, версию записи, допустимость перехода.
4. Создается `case_stage_events`, обновляется текущий этап, создается уведомление.
5. Клиент в Flutter видит новую запись в таймлайне.

### Сценарий D. Чат

1. Клиент в Flutter открывает диалог **выбранного** дела, пишет и добавляет разрешенное вложение.
2. Текст сохраняется с уникальным `client_message_id` и защищенными вложениями.
3. Назначенный сотрудник видит сообщение в React Web и отвечает.
4. Flutter и Web через Realtime обновляют беседу без лишних дублей; прочтение отражается отдельно.
5. При переназначении дела предыдущий сотрудник теряет доступ, история остается.

### Сценарий E. Чек и ручное подтверждение оплаты

1. Сотрудник с разрешением задает договор и платежный график.
2. Клиент видит сумму, даты, остаток и прикрепляет чек.
3. Чек имеет статус `pending_verification`, **не уменьшает остаток**.
4. Только сотрудник с `payments.confirm` подтверждает поступление, фиксируя сумму, дату, автора.
5. Остаток пересчитывается, клиент видит **подтвержденную** оплату. Любая корректировка — новой записью с причиной.

### Сценарий F. Блокировка или переназначение

1. Админ переводит дело другому юристу либо блокирует сотрудника.
2. Назначения/статус обновляются атомарно, событие аудируется.
3. Старый юрист больше не может прочитать данные прямым запросом или через старые подписки; защищенные временные ссылки должны иметь разумный короткий TTL.
4. Новый юрист получает положенную историю дела.

## 10. Требования к UI/UX

**Ориентир:** чистый, спокойный, профессиональный интерфейс юридического сервиса, без чрезмерной декоративности и «типичного AI-dashboard».

### Flutter Client

- До 4 основных пунктов нижнего меню.
- Визуальный приоритет: **«Что мне сделать сейчас?»**, затем этап и история.
- Крупные кнопки, минимум лишних карточек и границ, ясные формулировки юридических статусов.
- Цвет статуса **дублируется текстом**; доступность и контраст важнее glass-эффектов.
- Использовать фирменные цвета/логотип из утвержденных бренд-материалов компании, не подбирать произвольный бренд.
- Нативные паттерны камeры, выбора файла, клавиатуры, разрешений и системной навигации.
- Нет пустых фиктивных KPI, «AI score» и процентов успеха юридического процесса.

### React Staff

- Desktop-first рабочая панель с боковым меню, page header, поиском, таблицами.
- У юриста первым экраном должна быть **очередь работы** (проверки документов, задачи, сообщения), а не маркетинговая статистика.
- У менеджера — клиенты и коммуникации; у админа — организация, роли и шаблоны.
- Ролевые меню, общие компоненты интерфейса, удобное чтение PDF.
- Confirm dialog для изменения этапа, отклонения документа, подтверждения платежа, блокировки доступа.
- Каждое действие: `loading`, `success`, `error`, `empty`, `permission denied`.

## 11. Приоритеты и этапы реализации AI-агентом

### Фаза 0 — Осмотр и план

- Прочитать существующий репозиторий, ТЗ и этот файл.
- Определить, что уже реализовано; **не переписывать работающий код без причины**.
- Составить dependency map, описание Supabase target, risk register и пошаговый checklist.
- Уточнять вопросы только по блокирующим решениям; в остальных случаях применить решения этого документа и явно записать assumptions.

### Фаза 1 — Foundation, Auth и доступ

- Monorepo / apps, линтеры, type checks, тестовые пайплайны.
- Supabase миграции, базовые таблицы, constraints, RLS, SQL grants, тестовые данные.
- Auth email/password; защищенное создание клиента/сотрудника админом; MFA сотрудников.
- Роли: Flutter принимает только `client`, Web — только `lawyer`, `manager`, `admin`.
- RLS тесты на cross-tenant/cross-case чтение и запись.

### Фаза 2 — Сквозной вертикальный функционал

Реализовать *действительно работающий* путь **админ создает дело → юрист запросил документ → клиент загрузил → файл прошел проверку → юрист принял/вернул → клиент увидел результат**. Не считать сценарий готовым, если security pipeline отсутствует: разрешить mock только для локального теста и пометить production blocker.

### Фаза 3 — Дела / задачи / история

- Настраиваемые этапы, история, задачи, назначения, завершение.
- Flutter: Home/Case/Tasks. Web: lawyer workload/case detail, admin workflows.
- Конкурентная запись, журнал, тест переходов и доступа после переназначения.

### Фаза 4 — Сообщения / оповещения

- Case chat, attachments, unread, Realtime, идемпотентность отправки.
- In-app notifications и уведомления по срокам без дубликатов.
- Realtime подписки очищаются при logout, переходе между делами, изменении доступа.

### Фаза 5 — Договоры / платежи / менеджер

- Договоры, график, чеки, ручное подтверждение, остаток.
- Manager dashboard/client list, точечные права.
- Тесты невозможности клиентом подтвердить чек.

### Фаза 6 — Администрирование / безопасность / QA

- Roles/permissions, шаблоны, системные настройки, FAQ, аудит.
- Миграции, проверка file quarantine/antivirus, backup restore, мониторинг.
- Автоматические тесты, ручная приемка на Android/iOS и актуальных браузерах.
- Документация развертывания self-hosted в Казахстане и handover.

## 12. Проверки и критерии приемки

### Обязательный функционал

- [ ] Клиентский интерфейс **существует только в Flutter Android/iOS**.
- [ ] Сотрудники работают только в **React Web**, без Flutter staff UI.
- [ ] Общий **Supabase** для данных; нет самостоятельного backend-сервера.
- [ ] Вход email/password; публичная самостоятельная регистрация выключена.
- [ ] Сотруднику недоступен Flutter Client как рабочее приложение; клиент не может войти в Web Staff.
- [ ] MFA для сотрудников, управление активностью аккаунта.
- [ ] Один клиент может выбрать между несколькими своими делами; все разделы меняются синхронно.
- [ ] Главная отображает текущее дело, юриста, ближайшую задачу и последний статус.
- [ ] Клиент видит только опубликованные этапы; внутренние заметки не передаются вообще.
- [ ] Админ может настроить версию этапов и создать дело; юрист может менять этап по правилам.
- [ ] История этапов не перезаписывается, возврат требует причины, завершение требует результата.
- [ ] Файлы загружаются из камеры/галереи/файлов Android и iOS; PDF/JPG/PNG/HEIC.
- [ ] Валидация MIME, файловых лимитов и безопасность выполняются доверенно.
- [ ] Файлы в карантине недоступны до настоящего завершения проверки.
- [ ] Юрист может принять/вернуть файл; при возврате обязателен комментарий.
- [ ] Повторная загрузка создает новую версию и сохраняет историю.
- [ ] Клиент видит задачи и может ответить; юрист подтверждает выполнение.
- [ ] Диалог связан с конкретным делом, сообщения и вложения доступны только участникам.
- [ ] Realtime чат работает без дубликатов; переподключение не создает повторные сообщения.
- [ ] Чек в проверке не уменьшает сумму долга; частичный подтвержденный платеж уменьшает.
- [ ] Подтверждение платежа работает только у лица с `payments.confirm`.
- [ ] Уведомления ведут к правильному объекту нужного дела, без лишних повторов.
- [ ] Менеджер не может менять юридические этапы по умолчанию.
- [ ] Администратор не читает содержимое всех документов по умолчанию.

### Security и надежность

- [ ] RLS и минимальные SQL grants включены на каждой таблице с предметными данными.
- [ ] Замена UUID чужого дела/файла/задачи/чата/платежа не раскрывает данные.
- [ ] Прямое обращение в Storage по чужому пути заблокировано.
- [ ] Подписка Realtime не раскрывает сообщения и внутренние заметки других пользователей.
- [ ] После переназначения бывший юрист больше не читает дело через новый запрос.
- [ ] Сервисные ключи не попадают во фронтенд, сборки, логи и git.
- [ ] Все значимые действия записаны в аудит с актером и временем.
- [ ] Повтор загрузки/сообщения/подтверждения не создает дубли; нет ложного success.
- [ ] Одновременное редактирование сотрудников не затирает чужие изменения.
- [ ] База, файлы и бэкапы с реальными ПДн находятся на согласованной инфраструктуре в РК.
- [ ] Резервное восстановление проверено; есть документация аварийного восстановления.
- [ ] Android/iOS просмотр документов, permissions, безопасный background/resume и истечение сессии проверены на устройствах.

### Ориентиры из исходного ТЗ для нефункциональных требований

- До **5 000 клиентов**, около **100 одновременно активных пользователей**.
- При согласованной нагрузке: **p95 обычных API-запросов ≤ 1 сек** (без крупных файлов/внешних провайдеров), главная ≤ 3 сек на согласованном тестовом профиле.
- Резервное копирование не реже раза в сутки; параметры восстановления из раздела безопасности.
- Предусмотреть ручную QA-матрицу Android/iOS + актуальные браузеры Chrome/Safari/Edge; для Flutter не переносить механически требования WebView из старого ТЗ.

### Формат отчетов по каждому этапу

```text
STATUS: Done / Partial / Blocked
IMPLEMENTED: какие файлы, миграции и экраны созданы
SECURITY: какие RLS и негативные тесты проверены
TESTS: команды + реальный результат + что не проверено
KNOWN LIMITATIONS: ограничения, без сокрытия
NEXT: минимальный следующий работающий шаг
```

**Определение готовности:** фича готова только если данные сохраняются в Supabase, доступ проверен на серверной стороне, состояния ошибок обработаны, сценарий протестирован и результат доступен нужной роли. Наличие красивой кнопки без работающей логики — **не готово**.

## 14. Известные решения / вопросы заказчику перед production

Зафиксированы следующие решения: **Flutter client-only; React Web staff-only; Supabase-only; email/password; русский MVP; без онлайн-платежей, CRM, ЭЦП и push в первой версии**.

Нужно отдельно утвердить **до реальных пользователей**:

- Конкретный дата-центр/хостинг Supabase и резервных копий в Казахстане, безопасность и соответствие требованиям законодательства.
- Реальное антивирусное сканирование и безопасное преобразование HEIC/PDF-превью; без этой части функциональность загрузки **не считается production-ready**.
- Список услуг, этапов и допустимых переходов (пример банкротства в исходном документе — стартовая схема, не нормативно гарантированная процедура).
- Списки документов, инструкции и образцы, предоставленные юридической компанией.
- Идентификация/проверка клиента при создании учетной записи и при восстановлении доступа.
- Окончательные полномочия отдельных сотрудников (`payments.confirm`, `pii.full_read` и т.п.).
- Официальные тексты согласий, сроки хранения, порядок удаления и правила трансграничной передачи данных.
- Регламент приглашений по email, поддержки и блокировок.
