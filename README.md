# Современная защита / ModernSecure

Клиентский кабинет и рабочее пространство юридической команды: дела, этапы, задачи, документы, сообщения и оплаты.

Политика конфиденциальности и условия ТОО «Современная Защита», БИН 220140025162, опубликованы 2 ноября 2026 года штатным механизмом версий. Исходники, источники реквизитов, подготовленная форма удаления и границы production-проверки описаны в [документации юридического раздела](content/legal/README.md). Новая очередь запросов требует отдельного применения миграции 097 и развёртывания сайта; публикация текста не означает, что очередь уже работает.

Это инструкция для разработчика, которому передаётся существующий проект. Рабочие настройки и пять подготовленных аккаунтов находятся в [handoff](handoff/). По решению владельца эти данные включены в приватный репозиторий. Доступ к репозиторию даёт доступ и к этим реквизитам.

## Быстрый запуск

Нужны Git, Node.js и npm. Локальная сборка проверена на Node.js **26.9.0**, npm **11.19.1**. Минимум для установленного Next.js - Node.js 20.9; для повторения локальной среды можно установить проверенную версию. Для работы со служебными скриптами БД на Windows используйте WSL2 и храните проект в файловой системе Linux: скрипты проверяют Unix-права локальных файлов.

```bash
git clone https://github.com/shpshka/ModernSecure.git
cd ModernSecure
npm ci
npm run setup:local
npm run dev
```

Откройте **http://localhost:3000/login**. Для первого входа используйте `owner@modernsecure.test` и пароль из [handoff/accounts.json](handoff/accounts.json), раздел `accounts.owner.password`.

Команда `setup:local` создаёт `.env.local`, `.env.db.local` и `.workspace-accounts.local.json` в корне проекта. На macOS/Linux она устанавливает права `600`. Повторный запуск сохраняет содержимое уже существующих файлов. Команда не меняет базу и не создаёт пользователей.

**Локально запускается только приложение. Supabase остаётся общей удалённой базой:** изменения из локального приложения видны всем, кто работает с этим проектом. Схема и аккаунты уже существуют; для первого запуска миграции и очистка не требуются.

Остановить сервер: `Ctrl+C`. При занятом порте освободите `3000` или измените `APP_ORIGIN` в `.env.local` на фактический адрес и перезапустите сервер. Используйте один адрес последовательно: `localhost` и `127.0.0.1` имеют разные cookies.

## Аккаунты и права

Все пароли записаны непосредственно в [accounts.json](handoff/accounts.json). Это действующие реквизиты, а не примеры. После изменения пароля в Supabase сохранённый пароль сам не обновляется.

| Роль | Email | Ключ в `accounts.json` | Полномочия |
|---|---|---|---|
| Главный администратор | `owner@modernsecure.test` | `accounts.owner` | Все дела и настройки; назначение, изменение и отключение обычных администраторов |
| Администратор | `admin@modernsecure.test` | `accounts.admin` | Все дела и настройки; управление юристами и менеджерами |
| Юрист | `lawyer@modernsecure.test` | `accounts.lawyer` | Юридическая работа по назначенным делам |
| Менеджер | `manager@modernsecure.test` | `accounts.manager` | Клиенты, открытие дел, работа по назначениям |
| Клиент | `client@modernsecure.test` | `accounts.client` | Собственные дела, документы, задачи и сообщения |

Оба администратора имеют роль `admin`; главного отличает защищённый флаг `is_primary_admin`. Обычный администратор не может повысить себя, управлять другими администраторами или менять их финансовые права. Финансовые полномочия хранятся отдельно от роли; у двух переданных администраторов они включены.

Адреса `.test` используются как логины и не являются рабочими почтовыми ящиками. Эти пять аккаунтов уже подтверждены, поэтому можно входить по паролю без письма. Восстановление по email для них не доставит письмо: для почтовых сценариев нужен настоящий адрес. Обязательный MFA выключен; добровольно подключённый подтверждённый фактор учитывается при входе.

## Окружение

| Переменная | Назначение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | URL существующего проекта Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Публичный ключ для входа и запросов с ограничениями текущего пользователя |
| `SUPABASE_SECRET_KEY` | Серверные операции с файлами и административные скрипты; ключ имеет повышенные права и обходит RLS |
| `APP_ORIGIN` | Точный origin приложения, без завершающего `/`; локально `http://localhost:3000` |
| `DATABASE_URL` | Прямое подключение PostgreSQL для служебных скриптов; находится в отдельном `.env.db.local` |

`APP_ORIGIN` используется в ссылках подтверждения/восстановления и при проверке отправки файлов. При смене домена или порта обновите его и перезапустите сервер. `DATABASE_URL` не нужен клиентскому браузеру или обычному запуску Next.js. Приватные файлы хранятся в бакетах `modernsecure-files` и `modernsecure-previews`; сертификат БД уже есть в `supabase/certs/`.

Для обновления передаваемых реквизитов меняйте соответствующий файл в `handoff`, а рабочую копию в корне обновляйте отдельно. `setup:local` намеренно не заменяет локальные настройки. Не добавляйте серверному ключу префикс `NEXT_PUBLIC_`. [Описание ключей Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

## Состояние базы и начало работы

С миграции **20261018008500** новые регистрации сразу видны администратору в разделе **Клиенты → Новые регистрации**, включая аккаунты без подтверждённой почты и без заполненного профиля. В очереди также видны ранее созданные аккаунты без карточки; сотрудники и действующие приглашения сотрудников исключены. Список обновляется каждые 15 секунд, пока вкладка открыта и пользователь не работает с формой.

Кнопка **Одобрить карточку** создаёт карточку и связывает её с аккаунтом одним действием. ФИО и ИИН для одобрения не обязательны: до заполнения ФИО карточка подписана email. Подтверждение почты по-прежнему нужно для входа. Если карточка с таким email уже есть, интерфейс предлагает привязать подтверждённый аккаунт к ней, сохранив дела и историю.

В **Профиле** клиент может заполнить ФИО и ИИН до одобрения или добавить ИИН позже. ИИН проверяется на формат из 12 цифр; это не проверка личности. После сохранения ИИН в одобренной карточке самостоятельное изменение ФИО и ИИН закрывается, исправления выполняются через компанию. Изменение телефона и города в профиле обновляет связанную карточку. Одобрение и дополнение данных записываются в аудит без полного ИИН.

На момент проверки 17 октября 2026 года последняя миграция - **20261017008400**. Дел, услуг, сообщений и файлов нет. Существует связанная карточка клиента для `client@modernsecure.test`. Перечень в `accounts.json` содержит пять подготовленных аккаунтов; новые регистрации могут увеличивать общий список Auth.

Чтобы начать работу с делами:

1. Войти главным администратором.
2. В разделе **Услуги** (`/staff/services`) опубликовать услугу, её этапы и список документов.
3. В разделе **Клиенты** (`/staff/clients`) одобрить новую регистрацию или выбрать существующую карточку. Для карточки, созданной вручную, привязать подтверждённый аккаунт.
4. В разделе **Дела** (`/staff/cases`) создать дело для клиента и выбранной услуги.
5. Назначить на дело юриста и менеджера. После этого дело появится у назначенных сотрудников, а у связанного клиента - в кабинете.
6. Переписка по делу находится в разделе **Сообщения** самого дела; **Чат команды** (`/staff/chat`) предназначен для сотрудников.

Эти действия создают реальные записи в общей базе. Они описаны для получателя и не выполняются командой настройки.

## Проверки и рабочие команды

```bash
npm run lint
npm test
npm run build
npm run db:verify
npm run db:roles
node scripts/test-primary-admin-live.mjs
```

| Команда | Результат / воздействие |
|---|---|
| `npm run lint` | Проверка кода ESLint |
| `npm test` | Локальные тесты, включая временные базы PGlite; не заполняют общую базу |
| `npm run build` | Производственная сборка Next.js |
| `npm run db:verify` | Проверка таблиц, политик, функций, бакетов и служебных настроек существующей БД |
| `npm run db:roles` | Чтение действующих ролей и главного администратора |
| `node scripts/test-primary-admin-live.mjs` | Проверка иерархии ролей внутри транзакции с откатом |
| `npm run db:cron-status` | Состояние заданий напоминаний |
| `npm run db:migrate` | Применение новых миграций к общей базе; не требуется при первом запуске этой передачи |

`npm run test:live` - исторический набор сценариев со старыми QA-аккаунтами и делами. После очистки эти данные отсутствуют: набор не является проверкой «из коробки». `scripts/provision-test-accounts.mjs` также содержит старый адрес владельца; до использования его нужно адаптировать к `is_primary_admin` и подготовить необходимые услуги/дела. Для проверки текущих прав используйте отдельный `test-primary-admin-live.mjs`.

`db:inspect`, `db:plan`, `db:apply` предназначены для первоначального развёртывания и на текущей заполненной схеме останавливаются. `scripts/reset-workspace.mjs` - отдельный инструмент удаления данных, он не относится к запуску или обычному обновлению проекта. Миграция `008` и ряд служебных скриптов привязаны к исходному владельцу/ID проекта, поэтому перенос на новый Supabase требует отдельной адаптации; простой заменой URL копия базы не создаётся.

## Публикация

### На собственном Node.js-сервере

1. Установить зависимости: `npm ci`.
2. Подготовить `.env.local` командой `npm run setup:local` и установить `APP_ORIGIN=https://ваш-домен`.
3. Выполнить `npm run build`, затем `npm run start`.
4. Подключить процесс к менеджеру служб, HTTPS и обратному прокси. Ограничения тела запроса прокси должны учитывать размер файлов и общий multipart-запрос приложения.
5. Настроить почтовые redirect URL в Supabase, как описано ниже.

### В существующем проекте Vercel

1. Получить доступ к проекту `modern-secure` и проверить связь с `shpshka/ModernSecure`, веткой `main`.
2. Framework Preset: **Next.js**, Root Directory: корень репозитория, Install Command: `npm ci`, Build Command: `npm run build`.
3. Выбрать поддерживаемую Vercel версию Node.js; по документации на дату подготовки доступны **24.x** и **22.x**. Локальная проверка Node.js 26.9.0 не означает поддержку этой версии Vercel. Перед публикацией проверить сборку на выбранной версии.
4. В Environment Variables внести четыре переменные из `handoff/app.env` для нужного окружения. Для Production заменить `APP_ORIGIN` на точный публичный HTTPS-origin. `DATABASE_URL` приложению на Vercel не требуется.
5. После изменения переменных запустить новый deployment: переменные применяются к новой сборке. `setup:local` в Build Command добавлять не нужно.
6. Проверить вход, клиентский кабинет, роли и файловые операции по публичному адресу.

**Файлы до 20 МБ:** формы передают байты напрямую в закрытый `modernsecure-staging` по выданному сервером адресу. В Next.js приходит небольшой манифест; сервер повторно проверяет доступ и содержимое перед сохранением в постоянное хранилище. Скачивание и просмотр передаются потоком после проверки доступа и записи в аудит. Обычный multipart оставлен для файлов до 4 МБ. [Рекомендации Vercel по лимиту тела](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions). На опубликованном окружении отдельно проверьте CORS Storage, загрузку, просмотр и скачивание: локальный тест не заменяет проверку размещения.

Для временных копий предусмотрен `npm run staging:cleanup` (предпросмотр) и `npm run staging:cleanup -- --apply` (удаление копий старше 24 часов, до 1000 за запуск). Добавьте его в операционное расписание вместе с остальными командами очистки. Постоянные файлы команда не затрагивает. Подписанные адреса действуют 2 часа; временная копия не доступна клиентам для чтения. На аккаунт допускается до 100 подготовок загрузки за сутки.

Источники: [версии Node.js Vercel](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions), [переменные окружения Vercel](https://vercel.com/docs/environment-variables).

### Почта и обратные ссылки Supabase

В **Authentication → URL Configuration** задайте Site URL публичного приложения. Добавьте разрешённые Redirect URLs:

```text
http://localhost:3000/auth/callback
http://localhost:3000/auth/recovery
https://ВАШ-ДОМЕН/auth/callback
https://ВАШ-ДОМЕН/auth/recovery
```

Замените `ВАШ-ДОМЕН` реальным доменом. Настройте SMTP для регистрации и восстановления на настоящих email; утверждённых корпоративных SMTP-реквизитов в передаче нет. Согласия и юридические документы публикуются администратором в `/staff/settings/legal` после получения утверждённых текстов. [Настройка redirect URL](https://supabase.com/docs/guides/auth/redirect-urls).

| Нет настроек Supabase | Запущен ли `npm run setup:local`; лежит ли `.env.local` рядом с `package.json` |
| Нет дел или услуг | Это ожидаемое состояние после очистки; создайте услугу и дело по инструкции |
| Юрист/менеджер не видит дело | Назначение на дело и активность сотрудника |
| Ошибка входа | Значения email/password в `handoff/accounts.json`; не менялся ли пароль после передачи |
| Не приходит восстановление | Логины `.test` не принимают почту; для почтового сценария нужен реальный email и SMTP |
| Файл не отправляется | `SUPABASE_SECRET_KEY`, совпадение `APP_ORIGIN` с адресом браузера и лимиты хостинга |
| Скрипт требует права `600` | Повторить `npm run setup:local`; на Windows выполнять служебные скрипты через WSL2 |
| Переход между `localhost` и `127.0.0.1` теряет вход | Открывать один и тот же host и порт |
| После изменения `.env` поведение прежнее | Перезапустить dev-сервер; для production пересобрать/перепубликовать |

Существующие правила разработки находятся в [AGENTS.md](AGENTS.md). Перед изменением Next.js-кода читать соответствующие руководства установленной версии в `node_modules/next/dist/docs/`.
