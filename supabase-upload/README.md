# Подключение ModernSecure к другому Supabase

Этот комплект разворачивает базу для существующего приложения ModernSecure в другом проекте Supabase. Он содержит все 95 миграций текущей версии. Администратор активирует клиентов, юристов и менеджеров; администраторов назначает только главный. В комплект также входят временная загрузка файлов, очередь мобильных push-уведомлений, восстановление обязательных запросов документов, проверка версии ответа на задачу, корректный порядок сообщений и финансовые ограничения завершения дела.

Сайт и новые мобильные оболочки поддерживают кабинеты клиентов и сотрудников. Согласованные требования и актуальные инструкции: [apps/mobile_webview/README.md](../apps/mobile_webview/README.md).

Комплект создаёт структуру с нуля. **Пользователи, пароли, дела и файлы из старого Supabase автоматически не переносятся.** Данные старого проекта и его локальные настройки не изменены.

## Какие файлы запускать

В Dashboard нужного проекта откройте SQL Editor → New query. Открывайте соответствующий файл, копируйте всё содержимое и запускайте целиком от роли `postgres`.

| Шаг | Файл | Назначение |
|---|---|---|
| 0 | `00_INSPECT.sql` | Только чтение: проверить таблицы, Storage и текущую конфигурацию |
| 1 | `01_INSTALL_SCHEMA.sql` | Установить полную схему одной транзакцией |
| 2 | `02_CREATE_OPERATOR.sql` | Назначить существующему Auth-пользователю роль оператора управления |
| 3 | `03_LINK_CLIENT.sql` | Создать карточку и привязать подтверждённый аккаунт клиента |
| 4 | `04_CREATE_CASE.sql` | Необязательно: создать услугу с этапами и первое дело |
| 5 | `05_VERIFY.sql` | Проверить таблицы, RLS, функции, бакеты и Realtime |

Файл `01_INSTALL_SCHEMA.sql` не требует подстановки URL, ключей, паролей или email. В файлах 02–04 замените значения `REPLACE_…` перед запуском. Пользователь управления и клиент должны быть разными Auth-пользователями.

Если возникает ошибка, транзакция откатывается. Не запускайте только кусок установочного файла после ошибки. При сообщении `current transaction is aborted` выполните `rollback;`, выясните причину и повторите целый шаг.

### Если другой проект уже содержит данные

Сначала выполните только `00_INSPECT.sql`. Если в `public`/`private` уже есть объекты приложения или настроены Storage-политики, **не запускайте установку поверх них и не удаляйте их ради установки**. Потребуется сравнить существующую схему и подготовить отдельную миграцию. Установщик намеренно прерывается до изменений при обнаружении этих объектов. Имеющиеся Auth-пользователи сами по себе не мешают чистой установке: для них добавляются профили без изменения паролей.

Этот комплект не заменяет перенос существующих данных. Такой перенос требует отдельно согласовать, что переносить, экспортировать Auth и бизнес-записи с сохранением UUID, скопировать сами Storage-файлы и проверить связи. Простая смена URL не переносит данные.

## Порядок создания доступа

1. После установки создайте отдельного оператора через Authentication → Users. Убедитесь, что email подтверждён. Пароль задавайте в Supabase, не в SQL-файле.
2. Скопируйте его UUID в `02_CREATE_OPERATOR.sql`, при необходимости измените отображаемое имя, выполните файл. Этот аккаунт нужен владельцу для учёта действий; он входит в рабочее пространство сотрудников. Первого главного администратора нужно назначить отдельно согласно процедуре инициализации базы; этот скрипт не выдаёт ему флаг `is_primary_admin`.
3. Создайте клиента через Authentication → Users либо регистрацию сайта, затем подтвердите email. Для закрытого доступа можно отключить самостоятельную регистрацию в настройках Auth и создавать пользователей только через Dashboard/Admin API.
4. В `03_LINK_CLIENT.sql` укажите UUID оператора, email и ФИО клиента. Телефон и город необязательны. Скрипт связывает пользователя только после явного запуска владельцем; одно совпадение email при регистрации не открывает дела.
5. Скопируйте возвращённый ID карточки клиента в `04_CREATE_CASE.sql`. Введите название дела и услуги. Этапы в примере взяты из ТЗ как стартовый вариант; измените их под утверждённый процесс. Для существующей услуги задайте `selected_service_id`.
6. Войдите в сайт под клиентом. Дело появится после выполнения шага 4. Аккаунт без назначения ожидает активации; активированный клиент без дел видит пустой кабинет.

Повтор шага 2 для того же оператора и шага 3 для того же привязанного клиента не создаёт дубль. Шаг 4 блокирует повтор с тем же клиентом и названием дела. Шаг 1 повторять нельзя.

## Настройки Supabase вне SQL

SQL не настраивает почтовый сервис, адрес сайта или ключи приложения. В другом проекте задайте:

- Auth: провайдер Email и вход по паролю, подтверждение email.
- URL Configuration: Site URL `http://localhost:3000` для локального запуска.
- Redirect URLs: `http://localhost:3000/auth/callback` и `http://localhost:3000/auth/recovery`. Для рабочего домена добавьте такие же два HTTPS-адреса и измените Site URL.
- Для отправки писем клиентам подключите корпоративный SMTP. Встроенная отправка Supabase без собственного SMTP ограничивает получателей участниками команды проекта.
- Data API: схема `public` должна быть доступна; схему `private` не добавляйте к exposed schemas.
- Storage: `modernsecure-files` и `modernsecure-previews` должны оставаться приватными. Браузер работает с файлами через серверные маршруты сайта; публичные политики на `storage.objects` добавлять не нужно.
- Realtime: установщик добавляет сообщения в существующую публикацию `supabase_realtime`.
- Cron: при доступном `pg_cron` установщик создаёт `modernsecure-task-deadlines` и `modernsecure-payment-deadlines`. Проверьте их наличие и `active=true`. Если расширение не было доступно при установке, сначала включите Cron в Supabase, затем выполните расписания ниже через SQL Editor.

```sql
select cron.schedule('modernsecure-task-deadlines','0 * * * *',
  'select private.enqueue_task_deadline_reminders()');
select cron.schedule('modernsecure-payment-deadlines','5 * * * *',
  'select private.enqueue_payment_deadline_reminders()');
select jobname,schedule,active from cron.job where jobname like 'modernsecure-%';
```

Официальные справочники: [настройки Auth](https://supabase.com/docs/guides/auth/general-configuration), [адреса возврата](https://supabase.com/docs/guides/auth/redirect-urls), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [API keys](https://supabase.com/docs/guides/getting-started/api-keys), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Переключение текущего сайта

1. Сохраните локальную резервную копию текущего `.env.local` вне публичных файлов сайта.
2. Возьмите URL и API keys **из одного и того же другого проекта**.
3. По образцу `.env.local.NEW.example` замените в корневом `.env.local`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://REPLACE_PROJECT_REF.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_REPLACE_ME
SUPABASE_SECRET_KEY=sb_secret_REPLACE_ME
APP_ORIGIN=http://localhost:3000
```

Первые два значения используются клиентом. `SUPABASE_SECRET_KEY` используется только сервером для защищённых операций с файлами: ему нельзя добавлять префикс `NEXT_PUBLIC_` или помещать его в мобильный клиент. Старый секретный ключ не будет работать с новым URL.

4. Остановите dev-сервер и заново выполните `npm run dev`.
5. Войдите под пользователем, созданным **в другом проекте**. Старые аккаунты автоматически там не появляются.
6. Проверьте открытие своего дела, отправку сообщения, загрузку документа и скачивание своего файла. Под вторым клиентом убедитесь, что прямой URL первого дела не даёт доступа.

`.env.db.local.NEW.example` нужен только для отдельных прямых подключений к БД. Для выполнения этих SQL через Dashboard он не требуется.

**Не используйте существующие `db:apply`, `db:migrate` и скрипты сброса для другого проекта без отдельной адаптации.** В `scripts/database.mjs` целевой старый проект закреплён явно. `setup:local` также использует старый handoff. Этот комплект устанавливается через SQL Editor и не записывает фиктивную историю в `supabase_migrations`. Последующие обновления должны учитывать установленную версию из `SOURCE_MANIFEST.json`, а не повторно применять все старые миграции.

## Что покрыто из ТЗ

| Раздел | Что есть в SQL |
|---|---|
| Клиенты и несколько дел | Отдельные карточки, явная привязка Auth, версии услуг, этапы и история |
| Документы | Запросы, версии файлов, сессии загрузки, проверки, решения, возврат и отзыв |
| Задачи | Ответы, подтверждение ознакомления, проверка сотрудником, сроки и напоминания |
| Переписка | Сообщения, вложения, идемпотентность, непрочитанное и отметки просмотра |
| Договоры и деньги | Договоры, графики, частичные оплаты, чеки и отдельное подтверждение поступления |
| Согласия | Версии текстов, запись согласия пользователя, необязательное рекламное согласие |
| Доступ и аудит | RLS, роли, назначения, внутренние заметки, журналы действий и обращений к файлам |
| Помощь | FAQ, контакты, часы работы, реквизиты компании |

Это полная схема **текущего приложения**, а не заявление о выполнении всех требований ТЗ одним SQL. Отличия и отдельные работы:

- В ТЗ SMS-вход; текущие страницы и привязка аккаунта используют подтверждённый email и пароль. SMS потребует провайдера, лимитов и изменения кода входа и привязки пользователя.
- ТЗ предполагает отдельную панель сотрудников. По текущему запросу она отключена в сайте; управление через SQL Editor или отдельный служебный инструмент остаётся задачей владельца.
- В текущей модели администратор имеет широкий доступ к делам; строгий режим доступа администратора только по отдельным назначениям из исходного ТЗ потребует изменения политик и служебных функций.
- Реальные проверки формата файлов и генерация HEIC-превью выполняются сервером приложения. Отдельного антивирусного сервиса в текущем коде нет; наличие статуса карантина в БД не заменяет антивирус.
- Шаблоны услуг версионируются, но полноценные правила допустимых переходов, сроки этапов, редактирование шаблонов уведомлений и настраиваемые лимиты загрузок требуют доработки.
- Тексты юридических документов, реальные шаблоны документов и контакты компании не подставляются вымышленными значениями.
- Архивирование и утверждённое удаление, регион размещения данных, резервирование файлов и БД, мониторинг, нагрузочные испытания и приёмка WebView на устройствах не создаются этим SQL. Если для нового проекта нужен регион из ТЗ, его необходимо согласовать до создания проекта: SQL не меняет регион Supabase.

## Проверка комплекта

Из корня репозитория:

```bash
node scripts/build-supabase-upload.mjs
node scripts/test-supabase-upload.mjs
```

Первый скрипт пересобирает основной SQL из миграций и записывает контрольные суммы. Из миграции 008 исключён только старый email-зависимый блок назначения владельца. Исходные миграции не изменены.

Второй запускает точные SQL-файлы 00–05 в локальной PGlite с моделированием системных таблиц Supabase, создаёт обезличенные тестовые аккаунты и проверяет установку, привязку, создание дела, RLS между клиентами, ответы на задачи, запрет анонимного доступа и защиту от повторной установки. Это не проверяет реальный SMTP, Storage HTTP, Cron или настройки вашего другого проекта. Для них нужен шаг 05 и проверка работающего сайта после подключения.
